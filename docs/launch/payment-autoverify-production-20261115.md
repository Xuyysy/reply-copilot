# Production checkout automatic reconciliation hotfix (2026-11-15)

Motivation: order 132cd199-bf7e-40a6-957b-a8d327fcc7c8, Xiaodou ¥9.90 +400 permanent credits, was credited at 19:47:39 CST via authenticated user refresh while a signed Webhook was not received until 19:52:01 CST. User requested faster **both permanent-credit and subscription** payment confirmation in Production.

Changes are **website frontend only**: no API Worker source, D1 schema/SQL, merchant secrets, payment price/amount, entitlement, risk and ledger logic changes. A generic bounded auto merchant-checker starts after a verified user cashier click (or an actual Xiaodou WeChat QR render), only while the website is visible, for 8 maximum checks per original-order cashier marker over 15 minutes. Each verification invokes the existing user-authorized POST /refresh and then owner-scoped GET /orders/:id. The UI claims success only for credit status paid + creditedAt or subscription status paid + checkout.paymentConfirmed. Paid renewal periodStatus queued remains queued, not immediately active. All terminal/risk/manual_review states fail closed. No browser data can credit or settle an order, no payment starts or duplicate orders are created, POST budget enforced in localStorage across tabs, and server subscription refresh has authoritative rate limiting.

The credit checkout and account recovery watcher now use the same helper; subscriptions add a foreground, bounded local-read watcher (2.5s GET) rather than requiring manual clicking Verify payment, armed solely by original cashier navigation. Cashier native navigation remains untouched. On merchant API failures users can still use the existing manual status checks; payment webhook path remains primary.

Deployment requirements: full exact-SHA CI and independent production-build artifact, Production Pages-only deployment using existing guarded manual workflow, fixed rollback deployment ID and current Production live binding equality; no Worker deploy, payments, D1 SQL or Chrome Web Store actions. Users cannot be promised zero-latency across failed/slow payment providers; target is seconds after independently verified merchant success. Never mark active subscription for a queued renewal.

The subscription checkout polling is additionally gated on the cashier-open marker and capped at 48 foreground local GETs (~2 minutes active watching). Its periodic GET never runs for a merely created unpaid subscription that did not open a cashier. React pending-order actions preserve native cashier navigation, and marking a cashier cannot authorize settlement. On manual status verification, the existing original order is always used.
