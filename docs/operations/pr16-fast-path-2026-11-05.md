## Before / after

Both versions perform the existing account precheck on cold start (three
parallel account/entitlement/usage GETs). The account state is already cached
for 30s. It is not a replacement for per-request server authorization.

Before:

`Reply → bind → precheck → local prompt context → duplicate /me → GET active → GET request → POST generate → ACK → verified composer`

After:

`Reply → bind → precheck → parallel local profile/history/preferences + token-bound owner → POST generate → ACK → verified composer`

Fresh requests use zero recovery queries. Normal cached-account requests have
only the generate and ACK network operations. Explicit pending entries and
network/ACK/server conflicts retain the recovery route. If local state was lost,
the new POST is rejected by the existing atomic server guard before any new
upstream call. User recovery then looks up the real blocker. A different pending
envelope is fenced before abandoning that blocker, avoiding a late new-envelope
race. Existing ready results win; results from another post remain copy-only.
The rare two-request fencing operation remains subject to the existing 2/min,
6/hour abandonment limits. A transient limit produces a bounded actionable
message, never a silent/unlimited model retry.

Cached owner identity is associated with the actual auth token. Token changes,
invalidations and mid-load account switches cannot reuse another account's
identity. Server session/frozen-account validation is unchanged. Independent
local identity and pending reads overlap; prompt context is read once alongside
profile/preferences. Exact model prompt hashes are compared in the benchmark.

## Reproduction

With dependencies installed in the candidate and frozen baseline worktrees:

```sh
node scripts/benchmark-pr16-fast-path.mjs --baseline /private/tmp/reply-copilot-pr16-before-fast --samples 20 --network-ms 80
node scripts/benchmark-pr16-recovery.mjs
npm test
npm --prefix api run typecheck
cd web && npx tsc --noEmit
```

The normal benchmark drives the actual content/background/router/coordinator/
HostedAIClient/provider adapter/ACK/composer fixture with 80ms synthetic HTTP
latency and a fixed 35ms synthetic provider. D1 reservation is an isolated
synthetic 4ms boundary, not a measurement of live D1. Each sample starts a fresh
content/background VM; two warm-ups/version are excluded, measured versions
alternate order. Recovery comparison instead uses real isolated SQLite with the
full D1 schema and actual quota/ACK/recovery routes; its first provider never
returns. Four trials retain local pending state and four lose it per version.

Do not add all phase columns: the model is inside generate HTTP; precheck and
local reads overlap. End-to-end elapsed time is measured directly. These data
cannot establish that real Qwen/X replies meet 3s. Real-provider latency and
real-X acceptance remain user checks, without automatic paid testing.

## Safety / release

Full release gate, types and Worker dry-run results are recorded below. Mock
coverage includes sequential normal/different-post replies, known/lost pending,
restart, network/ACK uncertainty, slow/permanent providers, abandonment, late
results, repeated IDs, concurrent users/tabs, storage failures, free/paid/budget/
ledger invariants and draft/association protections. Especially: after a stuck
first request is abandoned, three subsequent successful requests have zero
recovery GETs and exactly three debits.

The standalone Staging bundle keeps only Staging API/site and existing
permissions, no debugger. Actual installed `02a8d9f` files are backed up first;
installation is opt-in at the same path to preserve the path-derived unpacked
ID `kaaehkpihjenlhjjfjcopkjhegmfmchk`, without uninstalling or clearing storage.
A hash-checked install/rollback script is provided. Do not load from the temp
worktree path under a different ID or relax Origin checks.

Worker rollback remains `1bab0bca-c151-43d9-a3af-00eff98edcad` only if a separate
server rollback is necessary; this client-only optimization does not require
one. Normal plugin rollback restores the saved `02a8d9f` files, while retaining
the currently deployed recovery-capable Worker and all business data.
Production and Chrome Store are untouched. PR #16 remains Draft/unmerged.
