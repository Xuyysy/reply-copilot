## 根因证据和归因限制

用户提供的 SQL Analytics 记录显示，无时间窗口、仅 request_id 关联、instr(reference_id,request_id) 和多层相关子查询可使核账读取达到百万级。本仓库当前 Worker、脚本和运维 SQL 中未找到这三条完整原 SQL；因此不能证明其调用者，也不能把事故直接归因于线上 Worker。自动巡检已在 ChatGPT 侧禁止 SQL，本次不重写该任务。

隔离重现采用完整0019表/约束/索引结构，合成每表2000/8000/20000行，不使用线上数据库：

| 历史表行数 | 旧缺分配核账 | 旧缺成本核账 | 旧分配/子串流水核账 | 新核账单页 |
|---|---:|---:|---:|---:|
| 2,000 | 2,003,000 | 2,003,000 | 4,004,000 | 1,400 |
| 8,000 | 32,012,000 | 32,012,000 | 64,016,000 | 1,400 |
| 20,000 | 未执行 | 未执行 | 未执行 | 1,400 |

旧查询的2000→8000行（4倍）带来约16倍读取，支持平方级扫描机制。为避免不必要的本机开销，旧全历史语句只测至8000行；新路径测至20000行。新核账默认24小时、每页200条；上述数据的24小时窗口恰有200条。结果完整性必须结合窗口、分页和 complete 标记理解，不能把200条视为全历史。

同为24小时范围，在20000行合成历史上，旧 request_id-only 缺分配/缺成本检查分别读取3,980,300 / 2,200,700行，新完整联合键核账读取1,400行；健康样本异常数均为0。另有注入异常测试验证不同账户复用requestId、流水前缀碰撞、免费/付费扣减桶不匹配及旧记录均被正确区分。

业务代码另有已证实问题：

1. `password-auth.ts` 的 `email=? OR username=?` 与 NOCASE 用户名唯一索引不一致；小写化身份还会令混合大小写用户名登录失败。Node SQLite 补 COLLATE 后可选索引，但**实际本地 workerd** 仍选择 SCAN users。改为两个独立、参数化的 UNION ALL 唯一索引分支后，workerd 计划为两次 SEARCH；没有新增登录索引，不改变密码/CSRF/限流/session检查。
2. `adminDashboard()` 原来对同一 ai_usage_costs 时间范围重复求和，之后模型明细再扫描一遍；现在从相同的全模型分组结果归并今日/本月总量，一次成本扫描，保留失败已产生费用、历史版本归属及共享预算预占。
3. 同一 dashboard 原来重复统计用户、流水和已到账订单；现在合并同表统计，并对非实时历史汇总以 DB 绑定为键缓存30秒（同日内）。鉴权、当前模型、开关、成本和全站预算每次请求仍读最新值；并发复用、UTC跨日、时钟回退和失败清缓存有边界处理。缓存仅对本 Worker 实例有效，不承诺全局命中率。
4. 全局最近流水、订单、审计和用户列表虽然已有 LIMIT，但缺少匹配排序索引；用户详情的 `(user_id,status,created_at)` 也不能直接按全状态时间倒序读取。这些路径由0020候选索引解决。

## 业务 SQL 审查覆盖

| 路径 | 现有证据/结论 | 本轮处理 |
|---|---|---|
| 注册邮箱/用户名占用检查、密码登录 | 邮箱唯一索引；用户名 NOCASE 部分唯一索引；OR可退化扫描 | 复用唯一索引的独立分支，验证正常/错误密码与混合大小写登录 |
| 限流 | rate_limits(bucket,period_start) 主键，原子 UPSERT RETURNING | 保留 |
| Session 认证 | token_hash 唯一索引 + users 主键 | 保留，不缓存身份或绕过账户状态 |
| 新人绑定领取 | 安装摘要唯一键、用户资格主键、同一D1.batch事务 | 保留，运行领取/并发/回滚回归 |
| 创建请求、ACK、重放、成本 | (user_id,request_id)联合主键/唯一键；账本(kind,reference_id)唯一键 | 保留所有写入与幂等门禁 |
| 余额/额度批次 | 用户主键与(user_id,bucket,status,...)索引；领取批次排序在用户范围 | 保留精确余额和预占 |
| 后台用户列表 | 现有200条上限、时间/关键字筛选；生成次数和活跃时间是按用户的精确查询 | 保留字段、筛选、生成次数；新增匹配排序/用户时间索引。包含式模糊搜索本质上仍可能扫描用户，未改成不同搜索语义 |
| 用户详情 | 用户ID点查；订单/流水已有用户时间索引；AI使用原来全用户历史排序 | AI用户时间索引；原100条上限和返回值不变 |
| 后台订单/全局流水/审计 | 原有100/200条上限，无全局时间索引 | 仅加索引；订单/支付业务逻辑不改 |
| 管理员模型测试 | 按测试ID、配置版本索引；30/min主键限流、全站预算主键预占 | 原无限每日次数、单次上限、预算和审计均保留 |
| 清理任务/交付过期释放 | 正常请求先做用户范围候选检查；真正发生过期释放时仍有全局更新/一致性断言 | 本轮不重写财务事务；列为后续高优先级专项，需独立并发/失败回滚实测后才能收窄范围 |
| 历史累计汇总 | 精确 COUNT/SUM 至少与历史规模线性相关 | 合并扫描并30秒缓存；未做物化累计表/财务重算 |

管理后台没有定时轮询；首次load、显式刷新、切入成本页和部分管理操作后会重新请求。30秒缓存缓解同一实例的密集重复读取，但不能消除首次全历史累计统计的读取成本。

执行计划要点：
- 登录：SCAN users → UNION ALL 两个唯一索引 SEARCH。
- 核账：先 MATERIALIZE 有时间范围/行数上限的候选页，再按完整 `(user_id,request_id)` 查分配和成本、按账本 `(kind,reference_id)` 精确查扣次、按批次主键验证扣减桶；没有instr/LIKE。复用现有索引，不为核账额外建索引。
- 全局最近流水/用户/订单/审计：表扫描与临时排序 → 按时间索引有界读取。EXPLAIN 中的 `SCAN ... USING INDEX` 可能只读取 LIMIT 所需前缀，不能仅凭 SCAN 一词断言全表扫描，应结合 rows_read。
- 用户AI详情：用户主键范围扫描并排序 → user_created 索引直接取100条。
- 成本与生成总量：全表/全成功状态扫描 → 时间范围 SEARCH。

## 0020候选索引的代价

`0020_d1_read_indexes.sql` 仅含7个 CREATE INDEX，不修改历史Migration、表/字段/约束或数据。每个索引都对应上面的实际查询和可测收益。

在每表20000行样本上，数据库约19,238,912→21,626,880字节，增加约2.28MiB。每个索引初建报告20,001行写入，合计140,007；真实数量取决于线上各表规模。因此**不能在Free日写入预算接近上限时直接建索引**，也不能把代码不改余额等同于索引没有写入成本。

| 合成插入 | 原 rows_written | 加索引后 rows_written |
|---|---:|---:|
| users 插入一行 | 4 | 5 |
| requests 插入一行 | 6 | 8 |
| costs 插入一行 | 2 | 3 |
| ledger 插入一行 | 4 | 5 |
| orders 插入一行 | 4 | 5 |
| audits 插入一行 | 2 | 3 |

这些是独立插入探针，不是完整AI生命周期总成本；UPDATE/ACK、DELETE、额外审计和其他既有索引也可能增加写入。尤其AI请求新增两个索引，必须把未来Free的100,000行/日写入预算一起评估，不能只看读取量。若实际业务写入瓶颈高于读取收益，可逐个审核索引；不盲目上更多索引。

## 低成本日常核账工具

```sh
# 输入必须是经批准取得的本机SQLite副本；默认最近24小时、200条、1页。
node api/scripts/audit-generation-credits.mjs --database /private/path/local-copy.sqlite --report-file /private/path/audit-report.json
# 显式确认扩展到最多7日；最多每页500、单次5页，不支持全历史。
node api/scripts/audit-generation-credits.mjs --database /private/path/local-copy.sqlite --since <epoch-ms> --until <epoch-ms> --confirm-expanded-window --limit 200 --pages 2
# 本地合成性能回归，外部访问被拒绝；不需要Cloudflare凭证。
D1_PERF_REPORT=/private/tmp/d1-query-report.json node --test api/tests/d1-performance.test.mjs
```

- CLI只有本地只读SQLite入口，没有--remote、数据库UUID、HTTP或环境执行选项；这些参数直接被拒绝。不会创建/导出线上数据库副本，本轮也没有读取旧生产备份。
- 返回 counts、窗口、执行次数和已有元数据，不额外执行统计SQL。只有Miniflare/workerd提供真实rows_read；Node SQLite CLI将其标为null并警告，不把返回行数伪装成消耗。
- 默认读预算5000行（可指定1～20000），达到预算后停止后续页并告警。即使末页不足limit而已读超预算，也会告警。预算是**执行后**保护，不能撤销首条查询的消耗。
- stdout不打印用户、请求标识或SQL参数。需要继续分页的私有cursor仅在明确指定的新报告文件中保存（0600，拒绝覆盖已有文件），库支持按固定窗口与cursor继续。CLI本版不自动遍历整个窗口，complete=false必须报告为未完整核账。
- `legacyUnattributed` 表示缺少足够的新流程证据，不能被当成已确认丢额度，也不能被直接宣称财务正确。旧成功记录没有新分配/成本/账本是可能的；强证据（ACK或分配记录）才进入现代一致性检查。
- 工具只报告，不修复、不发额度、不改历史。全历史审查应另立经明确授权的离线作业，在导出副本按窗口/页运行并独立审核；日常巡检不得调用全历史扫描。
- 运维默认通过Cloudflare Dashboard/GraphQL Metrics/SQL Analytics观察读取/写入总量、数据库和查询指纹。不能为获取指标额外发COUNT/SELECT。外部工具仍可能绕过本仓库护栏，流程和权限控制也必须保留。
