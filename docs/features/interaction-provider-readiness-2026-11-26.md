# Interaction workbench: active read provider candidate

## Scope and status

Base: `chatgpt/account-operations-staging-integration-20261126` at `01fefebd205d5d9b3bf9eb77c8adf0aee537d974` (PR #263). This increment targets that branch, not Production. Existing independent pages, rankings, IndexedDB v3 and source-specific checkpoints are retained. Follow V2 is unchanged and remains separately gated. No API/Worker, payment, AI, quota, manifest permission or database migration changes.

**Implemented is not live-accepted.** The new provider runs through the real page projector and Background/IndexedDB chain in isolated Chrome with synthetic network responses. No authenticated live X response was captured during development. Current X operation validity, account-specific access, real cursor termination, completeness and real rate-limit windows remain unverified. Do not promote this candidate as live-accepted on fixture results.

## Why the factory was null

`createAccountWorkbenchController` had an injectable `providerFactory = null`; `registerAccountWorkbench` never supplied one. This deliberately prevented starting network work. The old `interaction-interface.js` accepted only the side panel, required a visible notifications page, discovered a notification operation from Resource Timing, and returned only a notification source. Merely setting the factory to a function would not fix background authorization, hidden-tab validation or the missing post source.

The Staging registration now injects `createXInteractionProviderFactory(chrome)`. Constructor injection remains fail-closed for tests/callers that do not explicitly choose a provider. Required dependencies are the bound X tab, installed Staging content script, normal native X session, a uniquely identifiable self profile handle and readable numeric `twid`, and valid same-origin read endpoints. No new account API or cloud service is invented.

## Transport and synchronization

1. Existing side-panel entry binds an X tab and owner, then opens the same independent workbench. Opening/reading cached rankings does not start a remote data scan.
2. The user confirms a sync. Background opens one owner-bound connection, scoped by an opaque connection UUID and a noncredential session UUID.
3. Content script performs read-only same-origin GETs using native cookies and an in-memory CSRF header. The user expressly allowed this temporary page-local CSRF use during this task. The public web-client bearer is not a user's login token. No `auth_token` extraction, cookie API, credential forwarding, storage, logging, HAR export or authentication challenge bypass is introduced.
4. Notification source uses the existing validated notification route metadata when available, otherwise the known `/i/api/2/notifications/all.json` route. Post source uses `SearchTimeline` with owner-scoped `(@handle OR to:handle) -from:handle`, Latest ordering and 20 records. This covers observed inbound reply/mention/quote evidence, not all posts, likes or complete history. No passive user-response interception, DOM event collection or archive import feeds these jobs. Optional Resource Timing routing metadata contains operation paths and boolean feature flags only; no observed response data is ingested. No request URL or cursor is exported to the view.
5. If no current search routing metadata is available, a pinned public seed is used. A seed is compatibility data, not evidence it still works. Unknown structure, missing/ambiguous terminal evidence, repeated cursors, account changes and HTTP errors stop the task. There is no denial fallback, query-ID brute force or automatic retry. A 404/403 means the route/access must be reviewed, not bypassed.
6. Both sources use the existing engine and commit records/checkpoints together. Current owner and binding are checked around reads and commits. Duplicate relationships from both sources merge in IndexedDB. The provider checkpoint namespace includes a SHA-256-derived fingerprint of both public route specifications. A REST/GraphQL or query/feature change starts a fresh compatible namespace rather than sending an incompatible saved cursor; prior records remain and deduplicate. A completed source refreshes from its head on a later explicit sync; a partial source resumes its committed cursor.
7. Per-page requests time out after 12 seconds, spacing is at least 1.8 seconds across sources/sessions in that tab; at most 30 pages/90 seconds per page-side connection. Each of two sources receives at most 15 pages and 40 seconds per run. Incomplete/oldest checkpoints are prioritized; a page-limit result allows the other source its allocation while preserving the overall partial status. A time-limited or failed in-flight source stops the run and the next explicit run prioritizes the unfinished/older source. HTTP 401/403/429 stop without retry. A request timeout is reported as `time_limit`, distinct from explicit user cancellation. Rate exhaustion and `Retry-After`/reset metadata impose a page-memory cooldown that survives a new connection (at least 60 seconds, bounded at 24 hours). It is not cross-device or persistent account-wide rate attestation; X's own limits remain authoritative.
8. Connection acquisition is bounded at 12 seconds. Cancellation or timeout frees the Background slot; late connections are closed and cannot commit. Pending page-side handshakes are generation-fenced across cancellation/replacement, so a late fingerprint cannot resurrect an old session or cancel a newer one. Cleanup is idempotent and bounded to one second even if a transport fails to respond. MV3 restart retains checkpoints and reports an interrupted task, rather than silently restarting remote work. The original bound X tab must remain open; the workbench itself need not remain open while a started bounded job runs.

Identity is local corroboration (`twid` plus self-profile handle), **not independent server attestation**. Search responses have no viewer identity proof; only explicit actor/target relationships matching the bound numeric owner become events. Replies, quotes and mentions lacking that evidence are excluded. Profile selector or web schema changes fail closed.

## Verification plan and acceptance boundary

Automated tests cover connection timeout/cancel/late cleanup, scoped bridge sender/owner/source validation, no credential-bearing response messages, GET-only no-redirect requests, hidden bound tab, exact cursor forwarding, rejected unknown schemas, account changes, foreign targets, 401/403/429, cooldown, source dedup, native IndexedDB, interrupted MV3 state and release of a stuck slot. Existing build tests must continue to prove Production/development exclude these Staging tools and capabilities.

To complete live acceptance, use a dedicated logged-in test profile with the candidate Staging extension. No credentials should be provided in chat or uploaded to GitHub. Open the workbench from that X account, authorize one bounded sync and record only safe results: each source's status/reason, page count, stored relationships and account-isolation result. Inspect pagination against actual current endpoint schemas; stop on any challenge/denial/schema mismatch. Test account switching, manual stop, restart/resume, duplicate refresh and limiter behavior without intentionally exhausting platform quotas. No automatic posts, likes, follows, paid API calls or bulk collection. Existing ranking counts are observed relationships, not complete account totals.

There is no authenticated isolated X profile in the supplied execution context. Live acceptance is pending that test condition, not a claimed pass or a fabricated fixture result. This PR does not deploy Cloudflare, replace an installed extension or publish the store.

## Subsequent candidate work

Task summaries retain separate notification and post outcomes, including not-run sources after failure, with only status and numeric counters persisted. The UI reports these separately.

`interaction-manager/sync/auto-sync-policy.js` is an independently testable, transport-neutral opt-in scheduling state machine. Explicit consent, an independently approved provider, verified matching binding and a valid lease are required. Success or a page budget boundary may schedule the next interval; errors, rate limits, cancellation and interrupted leases pause. **This policy is not wired to a live provider, browser alarms or Staging settings.** No automatic network work or live readiness is claimed. No permissions changed; platform authorization and live acceptance remain independent gates.

The schedule policy now has a separate owner-scoped local IndexedDB store. Configure, claim, settle, disable and orphan recovery are transactional; two contexts cannot both claim the same waiting lease. Only projected schedule fields are persisted, not authorization evidence or session data. This is a local control-plane component, **not a browser alarm registration or automatic X request implementation**. A future approved host must establish authorization and current binding, execute or cancel its task, and coordinate recovery; disabling the stored schedule alone does not cancel an independently executing task. Native Chromium tests exercise persistence, concurrent claim, stale completion, account mismatch and interrupted recovery. Local ranking and detail share canonical merged evidence; five-type fixture coverage verifies counts, conflicting time, implicit mentions and CSV consistency. No live acceptance is implied.

Staging adds the explicit local `alarms` permission (Production/development unchanged), a transport-free one-shot schedule clock adapter and an owner-scoped interval preference in the existing interaction workbench. The checkbox remains disabled and the UI explicitly says the source has not been verified. Saving a preference does not grant consent, schedule a real task, register an alarm listener or call any provider. Tests cover clock bookkeeping and account-scoped preference isolation. Real automatic X requests remain unimplemented and must not be enabled from this candidate.
