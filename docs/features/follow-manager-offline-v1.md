# 互关助手 / Follow Manager — 官方归档免费版（候选 V1）

范围：独立 Chrome MV3 本地归档分析。相关产品需求 [Issue #243](https://github.com/Xuyysy/reply-copilot/issues/243)。

## 如何使用

1. 用户自行访问 X 设置 → 你的账户 → 下载个人数据归档，完成身份验证后等待 X 生成 ZIP（可能需要数天）。
2. 下载并解压 ZIP。**推荐**在 Chrome 插件「互关助手」页面拖入整个解压后的归档根目录，或点击「选择整个文件夹」。插件优先直接定位 `data/`，只枚举该目录下的文件名并读取 `follower.js`、`following.js` 和相应分片；不会遍历图片、视频、私信文件夹，不支持直接导入 ZIP。也可选择 `data` 文件夹本身。
3. 如果 Chrome 无法调用快速目录选择，页面会出现「兼容选择文件夹（可能较慢）」，使用浏览器目录输入；此模式 Chrome 可能预先枚举全部文件，因此大型归档优先采用拖拽方式。备用按钮「手动选择 JS 文件」仍可单选/多选，支持分次添加同类 partN；选择新的 part0 会重新开始该类别，防止混入另一份归档。填写所属 X 用户名并确认两组来自同一账号后，点击「导入并分析」。可在扫描时取消；「清空待导入文件」不影响已保存快照。
4. 查看“互相关注”“没回关我”“我没回关”列表。结果按归档中的数字账号 ID 展示，点击“打开 X 主页”可在 X 查询最新状态。导入时间不是 X 归档内容快照的确切生成时间；更改关注关系后必须重新请求/导入归档。
5. 支持搜索数字 ID、每页 50 条、导出当前筛选列表 CSV、本地快照重新加载和删除。不同 X 用户名以 IndexedDB owner key 分开存储。清除 Chrome 扩展数据也会清除快照。

## 安全与隐私

- 不上传整个 ZIP、私信、邮箱、Cookie、访问令牌或名单。文件夹模式只进入指定的 `data` 目录、按名称寻找目标 JS 文件并读取其文件头，忽略归档中的其他内容；手动模式只读取用户明确选中的 .js 文件；先从静态文件头判断 follower / following 类型，再解析 window.YTD.follower/following.partN 的 JSON 数组，绝不执行 .js。拖拽后仅保存文件对象供本次解析，首次选中不会保存源文件内容。
- 不调用 X API、不依赖 x.com DOM、不会调用 Cloudflare Worker、不会增加 Chrome cookies/scripting/tabs 权限；没有自动关注/取关。只有用户主动点击资料链接时才会打开 X。
- 严格校验 1–20 位数字账号 ID，保留 snowflake 字符串精度；目录扫描单层最多 4096 个条目、最多 16 个关注分片；每文件最多 32 MB、每类合计 128 MB、每类账号最多 25 万。拒绝非连续或重复分片。无法证明来自同一账号，因此通过用户手工确认归属，不要把名称输入当作官方身份验证。
- 用户文件内容只有数字 ID；没有 X API enrichment，因此不显示姓名、头像、近期取关、关注时长、总实时数据或按用户名搜索。仅能保证所选文件里包含的快照关系，不能保证用户已选齐所有隐藏分片。
- 所有文件在扩展内部页面中处理，使用 IndexedDB 最小化持久化两个 ID 数组，不放进 chrome.storage.local 或账户后端。

## 网页扫描（Staging 实验路线，2026-11-23）

根据用户明确要求，在原有归档本地分析之外提供 **无需申请 / 下载 / 导入 X 归档** 的可选入口：

- 在互关助手页显式点击「体验网页扫描」，打开独立 `follow-manager/web-scan.html`；用户输入自己的 X 用户名、勾选主动扫描与平台风险确认，再点击「开始网页扫描」。
- 扩展使用原有 X 内容脚本匹配机制注入 `content/follow-dom-helpers.js` 与 `content/follow-web-scanner.js`，无需新增 `cookies`、`scripting`、`tabs`、X host 权限。扩展页通过已创建 X 标签页的 ID 发送消息，先访问 `/{owner}/following`，再访问 `/{owner}/followers`。
- 读取当前 X 页面主列可见用户卡片中呈现的 **@用户名**（不是隐藏 React Store 或接口响应）。主动滚动最多约 4 分钟／类别、最多 3,000 个可见账号；提供进度和停止扫描。仅在用户账号导航可见时核对登录用户名；页面跳转、超时、空列表、扫到上限必须显式反馈。
- **不读取 Cookie、会话凭据；不自行调用 X 内部 GraphQL 或收费官方 API；无后台数据上传；不点击关注/取消关注；不执行自动取关。** 网页本身为正常加载会发出网络请求，这与扩展主动抓取接口不同。
- 扫描得到的是两个不保证完整的 **网页可见用户名快照**，并非数字 Snowflake ID 或可证明完整的关注关系。两组交集标「观察到双方互关」，差集统一标注「疑似未回关」，不能当成最终结论；推断结果会受虚拟滚动、页面广告/推荐卡、X 动态加载、网页变更、改用户名和 rate limit 影响。
- 两轮都观察到列表底部时，将观察快照保存在独立 IndexedDB 数据库 `xrh-follow-web-v1`；**即使观察到页底，也不能保证完整**。任一轮达到数量/时间上限，展示临时部分结果但不覆盖已存快照；取消/错误也不保存。
- 本功能只在 Draft PR 的 Staging ZIP 中供人工验收；账号可能触发风控，网页自动化可能受 X 条款限制，技术可行性不代表商业发布合规性。生产版仍不得未经独立审批引入或默认开启该实验功能。

**Staging 实测清单：** 完整 X 登录账号、两页路由与登录身份校验、日/夜主题、非英语页面、真实虚拟滚动是否漏人、进度与停止、分页/CSV、仅观察到页底时 IndexedDB 保存/回读/删除、时间/人数上限、关闭页面/换账号、现有 AI 回复悬浮窗与账户额度是否不受影响、Network 检查扩展没有上传名单。与之前官方归档的 25 万数字 ID 快照应独立存储，不能静默合并或互相覆盖。

## 内部网页接口快速同步（新增 Staging 测试模式，2026-11-23）

用户明确要求在已实现的官方归档导入和只读 DOM 页面扫描之外，新增一个可以在 Staging 实测的 **X 网页内部 GraphQL 关注关系同步模式**；不使用 X 收费开发者 API。参考开源 [huangsen365/x-follow-checker](https://github.com/huangsen365/x-follow-checker) 的分页游标处理思路，项目自己的解析、鉴权边界、前端 UI、存储、测试均独立实现，并非复制原仓库业务代码。

- 导航：`follow-manager/manager.html` 新增单独的「快速同步（测试）」入口，进入 `follow-manager/internal-sync.html`。三条模式（网页 DOM、内部接口、官方归档）并存，方便在同一 X 账号下对比人数、耗时和结果。
- 用户必须主动输入当前登录 X 的用户名、勾选确认本人账号后启动。与 DOM 模式一样，扩展页创建临时 `chrome.tabs.create({active:false})` X 标签页，不抢占焦点；依次打开 `/{owner}/following`、`/{owner}/followers`，进度按页展示，真实计时。完成/错误/取消/关闭扩展页时尝试清理临时页。
- 已注入的内容脚本 `content/follow-internal-helpers.js` 和 `content/follow-internal-scanner.js` 仅在该模式收到插件的 `XRH_INTERNAL_START` 消息时运行。使用 X 网站现有登录态，只有同源 `https://x.com/i/api/graphql/*` **GET** 请求；从当前页用户导航校验当前账户确为目标账户，`UserByScreenName` 得到 ID，逐页读取 Following / Followers，解析可识别的用户名和精确字符串 ID。**此处是非公开 Web API，不是正式向第三方开放的免费 API；接口 query ID 和特征参数可能随时失效。** 新增优先从当前 X 页面同源 Performance Resource Timing 中已加载的 GraphQL URL 提取当前查询 ID（不主动读取或执行网页 JS bundle），取不到时才用兼容默认值；失败时返回明确的接口版本提示，不做无限重试。
- 不请求 Chrome `cookies` 或额外 X host 权限；只在 X 页面上下文从 `document.cookie` 中取非 HttpOnly 的 **ct0 CSRF Token**，只传给 X 自身的请求头；不读取 `auth_token` 的值，不向扩展 UI/Worker/Cloudflare 传递任何 Cookie/Token，不持久化、不打印。X 网页自身的登录 Cookie 由浏览器按同源规则携带。若用户设备未暴露 `ct0` 或接口行为发生改变，会显示登录/接口错误，并停止，不绕过限制。
- 只读，不点赞/关注/取消关注；按用户 ID 去重，单类最多 3000 人、160 页、最长 5 分钟；分页请求间隔约 1.8 秒以限制频率。401/403、429、404、网络/接口结构变化、重复游标、超时、页面变化均停止或标记不完整；不尝试规避限流。不记录原始 JSON/CSRF 数据。
- UI 显示分页进度、两组人数、真实已用时间、停止、三个关系分类、按用户名筛选、50/页、个人主页链接与 CSV；两轮都明确读完才保存到独立 IndexedDB `xrh-follow-internal-v1`，否则结果仅限本次展示、不能覆盖以前保存的快照。原 DOM `xrh-follow-web-v1`、归档数字 ID 存储均保持不变。
- **限制：** 本方法可能违反 X 的自动访问规则，带来账号限制风险；即使无收费 API 成本也不等于被平台授权。仅 Staging 试验使用，公开商业化发布前必须单独评估合规与 Chrome Web Store 规则。实际数据与速度、账号会话和 X 接口响应均需要用户真人 Chrome 实测，不可由 CI 证明。
- **项目隔离：** 不修改现有 AI 回复/200 次免费额度/支付/Cloudflare Worker/Pages/D1 等业务代码，禁止自动发布到 Production 或 Chrome Web Store，不执行远端 D1 SQL。

## 关注关系 V1.1：本地缓存、续扫、历史变化与蓝 V 筛选（2026-11-23）

根据用户反馈「不必每次重复扫描」以及「列表增加蓝 V 账号筛选」，在 **同一 Draft PR #244** 持续完善；保持原 Production 不变。

- **打开即显示旧结果：** 网页 DOM 与内部接口模式独立记录上次使用账号的用户名（extension localStorage），页面打开即从各自 IndexedDB 自动恢复**上一份完整快照**，标记扫描时间及「超过 24 小时」的过期提醒；**从不自动重新请求 X**。用户点击「更新关注关系」才实际扫描。切换账户时按账户读取，不跨账户混用数据。
- **更新时保留旧数据：** 启动新一轮不会清空已经展示的上次完整结果。失败、取消、限制或不完整结果不会覆盖已有完整快照。用户可以随时复查上次的缓存名单。
- **第一轮续扫：** 第一次关注列表完整扫描后保存本地短期检查点（单独 IndexedDB pending store），第二轮粉丝名单失败或页面关闭后，30 分钟内允许复用第一轮完整名单，重新执行第二轮；重开页面会显示「继续上次未完成的同步」。检查点不直接作为完整互关结果，不跨账号复用，成功保存两轮快照时自动清理；过期后完整重扫。因两次名单可能在不同时间获得，仍以快照时间和数据完整性标记。
- **历史及变化：** 完整快照按账号保留最近 5 份历史（从原 v1 数据库原位升级到 v2，不删除旧数据），与上一份比较新增/减少的粉丝数。内部接口同时保存精确字符串用户 ID，后续比对尽量按稳定 ID，以减少改用户名的误判；旧记录或 DOM 仅能按用户名估算，界面说明可能受改名、漏加载影响，**不声称绝对取关事实**。
- **蓝 V 列表筛选：** 两种模式各增加「全部账号 / 仅看蓝 V / 确认非蓝 V / 认证状态未知」下拉选择，与关系分类和关键词搜索共同生效；列表中明确识别为蓝 V 的账号显示蓝色小标签，导出 CSV 新增 `blue_verified` 列。内部接口仅使用返回的显式 `is_blue_verified` 布尔值（不把金 V 企业和灰 V 政府账号当蓝 V，不从泛化 legacy.verified 推断），DOM 仅当用户名区域认证图标颜色明确为标准蓝色时标记；无法确定时**统一为未知而非非蓝 V**。旧缓存无认证字段默认未知；归档数据仅有数字账号 ID，未通过额外请求补充蓝 V 信息，因此归档模式不提供误导性的认证筛选。
- **存储隔离和安全：** 共享 `follow-manager/follow-snapshot-store.js` 仅封装存储逻辑，依然使用两个原来的独立 DB 名称；不新增 Chrome 权限、不上传 Cookie/Token/关系数据、不扩展收费 X API 调用，也不自动关注或取关。
- **修复：** 内部接口结果页的分类切换原使用 `dataset.webKind`（错误），已改为 `dataset.internalKind`，让互关/疑似未回关切换实际生效。
- **待 Staging 验收：** 旧 IndexedDB 数据升级且仍能读取、重新打开默认不发 X 请求、刷新后更新、只成功第一轮时复用检查点、超过 30 分钟回退全新扫描、蓝 V 识别对照 X 实际徽章（金/灰不能误标）、筛选 + 搜索 + 分类 + CSV 结果一致、更新失败不覆盖旧完整结果、取消与 Chrome 后台页面节流行为。

## 2026-11-23｜快速同步大名单分批续传与粉丝接口兼容修复（Staging 候选）

用户在实际 Chrome Staging 看到「我关注的人：3,000（达到同步上限）」和「关注我的人：0（X 网页接口已变化）」。**这里的 0 表示未能取得粉丝名单，绝不是对真实粉丝数的断言**。以前内部模式将 3,000 人作为单名单最终上限，也只支持第一轮「完全完成」后的单检查点，超过 3,000 人就只能反复从头读取。

### 此次修正

- **接口兼容性：** 借鉴近期 GitHub 项目 `anatolykoptev/go-twitter` 中记录的 X Followers/Following 读取从 GET 改为 POST 的实现，更新这两个**只读 GraphQL 查询**的传输为 `POST /i/api/graphql/<id>/Followers|Following`，JSON body 包含 `variables` 和 `features`，加入 `withGrokTranslatedBio:true`。个人资料 `UserByScreenName` 仍为 GET。此 POST 是读取，不包含关注/取关等 mutation。仍只使用 X 当前网页登录态发往 X 同源，不上传会话凭据或名单；不会对 429 做自动重试、变换身份或绕过限制。**非公开接口仍可能随时变化，具体能否修复用户账号的响应需 Chrome Staging 实际确认。**
- **解析兼容：** 按新的结构接受 `core.screen_name`（保留 `legacy.screen_name` 后备），兼容 `TimelineAddEntries`、`moduleItems`、不同层次的用户数据包装；不确定是否已经读到列表末尾时不能宣称完整。
- **从 3,000 最终上限改成分批：** 每次用户主动点击最多新增约 3,000 用户、最多 120 页 / 4 分钟，本地单名单累计保护上限 30,000 人。达到单批预算时**暂停并保存下一页游标**，不再把 3,000 人当整个列表的总数。用户下一次点击「继续同步」从游标继续，重复 ID 去重。仍遵守 X 自身速率限制、429 立即停止，不会自动连续批量请求。
- **断点续传细化到每个阶段：** `following`、`followers` 分开保存累计用户名、精确字符串 ID、蓝 V 字段、游标、页数；每 8 页顺序写入本机 IndexedDB pending。关闭页面或部分失败后，在 24 小时有效期内可从最后成功保存的页继续。若关注名单已完成，后续只继续粉丝名单。原 2026-11-23 的「30 分钟/第一轮完成才可复用」逻辑升级为「24 小时/分页续传」，但因两次采集可能跨时段，完成的快照仍不是同一瞬间的实时数据。
- **明确状态：** 401/403 登录失效、429 限流、404 查询地址变更、400/422 参数版本不匹配、GraphQL errors、无法解析数据、重复游标、超时等在 UI 采用不同中文提示；未获取任何粉丝时显示 `—`，不再展示误导性的 0。停止、失败不保存为完整互关结果；旧完整快照不被覆盖。
- **手动重置进度：** 允许用户在不删除上次完整名单的前提下，单独清除损坏或过期的续传状态并重新开始。两类名单都确认完整才通过现有原子事务写入正式快照，原有蓝 V 筛选、历史、CSV 不变。
- **风险/发布边界：** 这是用户自愿启动的非公开网页接口测试，不是 X 授权的免费开发者 API，也无法保证超过 30,000 人时获取全部账号。任何 401/403/429 都不绕过。仅 Draft PR/Staging，未变更 Production、Cloudflare Worker/Pages/D1、支付、AI 回复业务、Chrome Web Store，也没有执行远端 D1 SQL。

### 必须真机验收

1. 用已登录 X 的 Staging 测试两个列表是否都可用；尤其看粉丝页是否还报 HTTP 404、400 或 GraphQL schema 错误。
2. 拥有超过 3,000 个关注的账号完成第一批后，再点「继续同步」，确认总数增长且不会从头读取；另一组失败后继续只读取未完成的那一组。
3. 中途停止/关闭页面再打开，验证读取旧快照与续传游标的独立性、蓝 V 与 CSV 过滤准确、24 小时过期及重置进度。
4. 确认遇到 429 不自动重试、未获得粉丝数据时不显示 0 个真实粉丝、不生成或覆盖完整互关结果。Chrome 后台标签可能被限制速度，CI 不能替代真实 X 服务兼容测试。

## 结果优先与一次启动完整同步（2026-11-24，Staging）

- 用户要求去掉两张实时关注/粉丝计数卡片，不必每批反复点击，也不必每次打开重读。快速同步页现在使用简洁的启动/更新按钮、加载计时、可停止操作与折叠账号设置；完成后直接显示三类关系、蓝 V 筛选、搜索、分页及 CSV。查看本地完整结果不调用 X；刷新才发请求。
- 原有每批工作预算、30,000 人本地保护上限、分页间隔不变。一次用户主动启动后，普通本地批次暂停时在同一任务内串行继续，仍保存检查点。仅在批次结果为 paused、游标推进且状态有效时继续；限流/权限错误/网络异常/重复游标/停止/总时间预算（45 分钟）立即停止，不自动重试。每类最多 20 个内部批次，不保证任意规模均能一次完成。

- 不改 X 请求频率、Chrome permissions、后端或 Production。真实账号接口兼容及 Chrome 后台执行仍待验收。关闭助手会终止本次任务，之后可从保存进度继续。
